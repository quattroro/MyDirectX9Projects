# 상세한 프롬프트가 기본 기능을 없애고 버그를 늘린 이유

2026년 11월 15일 · @quattroro

자세히 쓸수록 모델은 쓴 것만, 쓴 대로 만든다. "breakout 만들어줘" 한 줄은 검증된 기본 템플릿(ESC 메뉴, 마우스 조작, 안정적인 충돌 처리)을 끌어내고, 세세한 스펙은 그 템플릿을 덮어쓴다. 그래서 요청한 기능은 다 들어갔지만, 템플릿이 공짜로 주던 기능과 완성도는 빠졌다.

레퍼런스(익숙한 예제) 효과는 실제로 있지만 원인은 하나가 아니다. 기능이 사라진 것과 버그가 생긴 것은 원인이 다르다.

## ESC 메뉴와 마우스 조작이 사라진 이유

상세한 목록이 "이게 전부"라는 신호로 읽혔다. 최신 Claude 모델은 프롬프트를 문자 그대로 해석하고, 하지 않은 요청을 추측해서 채우지 않는다 ([Anthropic 프롬프팅 가이드](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)).

|   |   |   |
|---|---|---|
||한 줄 요청|세세한 스펙|
|모델이 읽는 뜻|완성도 있는 브레이크아웃을 기본값으로 채워라|적힌 것이 요구사항 전부다|
|ESC 메뉴, 마우스|기본 템플릿에 있어서 들어감|언급이 없어서 빠짐|

특히 스펙에 조작키를 "←/→ 또는 A/D 이동, Space 발사, P 일시정지, Enter 시작/복귀"로 명시적으로 나열했다. 이렇게 쓰면 마우스와 ESC는 빼라는 뜻으로 읽히기 쉽다. 일시정지를 P로 정한 순간 ESC 메뉴 자리도 사라졌다.

공식 가이드도 이전 모델처럼 기대 이상으로 해 주길 원하면 최신 모델에서는 그걸 더 명시적으로 요청하라고 안내한다. 예시로 "관련 기능과 상호작용을 최대한 넣고 기본을 넘어서라"는 문장을 붙이는 방법을 보여준다 ([Claude 4 best practices](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/claude-4-best-practices)).

## 세세한 버그가 생긴 이유

세 가지 원인이 겹쳤고, 표본이 1회라는 점도 감안해야 한다.

### 1. 익숙한 템플릿에서 벗어났다

일반 브레이크아웃의 충돌 처리는 수없이 검증된 패턴이라 모델이 안정적으로 재현한다. 변형 스펙의 항목들은 모두 그 패턴 밖이다.

|   |   |
|---|---|
|스펙 항목|템플릿이 깨지는 지점|
|체력 2인 벽돌|"맞으면 지우고 vy 반전"이 안 통하고, 어느 면에 맞았는지 정확히 판정해야 함|
|벽돌 하강|충돌체가 움직임|
|공 분열|여러 공 × 동시 충돌 × 라이프 판정이 얽힘|
|테스트 API와 고정 좌표 공식|튜토리얼과 다른 코드 구조를 강제함|

### 2. 두 변수가 동시에 바뀌었다

"그냥 breakout"과 "변형 규칙 + 세세한 스펙"은 다른 게임이다. 게임 복잡도와 스펙 상세도가 함께 바뀌었으니, 버그가 어느 쪽 때문인지 지금 결과로는 구분할 수 없다. 상세도만의 효과는 S1(같은 변형 게임 + 한 줄 요청)과 S2를 비교해야 보인다.

### 3. 주의가 체크리스트로 분산됐다

정확한 수치, 테스트 API, 시드 난수 같은 조건이 많으면 노력이 "목록 맞추기"로 간다. 검증 지시가 없으면 목록을 다 채운 시점에 끝났다고 판단하기 쉽고, 실제로 돌려서 확인하는 과정이 빠진다.

### 표본 수

조건별로 한 번씩 돌린 결과라서 운의 영향도 꽤 있을 수 있다.

## 정리

"자세히 안 쓰는 게 낫다"가 아니라 "자세히 쓸수록 쓴 것만, 쓴 대로 만든다"에 가깝다. 짧은 프롬프트는 모델의 기본값(검증된 템플릿)에 맡기는 것이고, 긴 스펙은 그 기본값을 덮어쓴다. 원하는 기능을 얻는 대신, 템플릿이 공짜로 주던 완성도는 직접 챙겨야 한다.

## 실험에 추가할 조건

아래 네 조건으로 위 원인들을 하나씩 떼어서 확인할 수 있다.

|   |   |   |
|---|---|---|
|조건|바꾸는 것|확인할 것|
|최소 요구사항 선언|S2 앞에 "아래는 최소 요구사항이고, 완성도 있는 브레이크아웃에 기대되는 기능(일시정지 메뉴, 마우스 조작, 시각 효과 등)은 자유롭게 추가해도 된다"는 문단 추가|빠진 기본 기능이 돌아오는지|
|방법은 자유|수치와 규칙(무엇)은 고정, 충돌 처리 방식(어떻게)은 가장 견고한 방법을 쓰라고 맡김|템플릿 이탈로 인한 버그가 줄어드는지|
|단계적 요청|"breakout 만들어줘"로 기반을 만든 뒤, 체력 벽돌 → 하강 → 분열 → 콤보를 턴마다 하나씩 추가|한 번에 긴 스펙을 주는 것보다 나은지|
|자기 검증 (V1/V2)|테스트 작성·실행 또는 브라우저 플레이 확인 지시|버그가 검증 부재 때문이었는지|


### 단계적 방식이 유리한 이유

- **각 단계가 익숙한 패턴 안에 머물러요.** “breakout 만들어줘”로 검증된 기반을 얻고 나면, "체력 있는 벽돌 추가"는 그 위에 얹는 작은 변경이라 모델이 잘 다뤄요. 한 번에 다 주면 여러 규칙이 얽힌 처음 보는 게임을 통째로 짜야 해요.
- **버그를 바로 찾을 수 있어요.** 기능 하나 추가 → 플레이·테스트 → 다음 기능 순서로 가면, 버그가 생겼을 때 원인이 방금 추가한 기능으로 좁혀져요. 한 번에 만들면 충돌 버그가 분열 때문인지, 하강 때문인지, 체력 처리 때문인지 알기 어렵죠.
- **원하는 게 만들면서 구체화돼요.** 말씀대로 모든 경우를 미리 다 떠올리는 건 불가능하고, 실제로 플레이해 봐야 보이는 것들이 많아요.

### 주의할 점

1. **나중에 바꾸기 어려운 건 처음에 정하세요.** 게임 개발에서 아키텍처를 먼저 정하는 것과 같아요. 이번 실험이라면 이런 것들이에요.
    
    - 고정 타임스텝, 시드 난수 (결정론적 동작)
    - 테스트용 `window.game` API
    - 공을 처음부터 배열로 관리하기. 공 하나 전제로 짠 코드에 나중에 분열을 넣으면 곳곳을 뜯어고쳐야 해요.
    
    그래서 첫 요청은 “breakout 만들어줘”에 **구조 제약 몇 줄 + "필요하면 일반적인 기능은 자유롭게 넣어도 된다"** 정도가 적당해요.
2. **덧붙일수록 코드가 누더기가 될 수 있어요.** 기능을 계속 얹으면 땜질식 분기가 쌓여요. 3~4개 기능마다 "지금 구조를 정리하고, 동작은 바꾸지 마"라는 리팩터링 턴을 넣어 주세요. 이때 테스트가 있으면 안심하고 정리할 수 있어요.
3. **단계마다 검증하세요.** 단계적 방식의 장점은 매 단계 확인할 때만 살아나요. 기능을 붙일 때마다 "테스트 작성하고 돌려서 통과시켜"를 같이 요청하거나 직접 플레이해 보세요. 단계마다 git 커밋을 해 두면 망가졌을 때 되돌리기도 쉬워요.
4. **대화가 길어지면 새로 시작하세요.** 한 세션에서 너무 오래 덧붙이면 컨텍스트가 무거워지고 초반 결정이 흐려져요. 큰 단계가 끝나면 요약을 CLAUDE.md나 메모 파일에 남기고 새 세션에서 이어가는 게 좋아요.

### 놓친 경우를 찾는 다른 방법

모든 경우를 혼자 떠올리지 않아도 돼요. 모델에게 먼저 물어보게 하는 방법도 있어요.

> "이 기능을 구현하기 전에, 내가 정하지 않았지만 정해야 할 것들과 예상되는 엣지케이스를 먼저 질문해 줘."

이러면 "공이 8개일 때 금색 벽돌은?", "마지막 벽돌과 마지막 공이 같은 프레임에 사라지면?" 같은 질문을 모델이 먼저 꺼내요. 그중 중요한 것만 답해 주면 돼요.

정리하면 **구조 제약은 먼저 → 기능은 하나씩 → 매번 검증 → 주기적으로 리팩터링**이에요. 다만 이것도 "한 번에 긴 스펙"과 비교한 데이터는 아직 없으니, 실험 조건에 단계적 요청을 넣어서 직접 확인해 보시면 좋겠어요.


# AI 에이전트와 누더기 코드 없이 안정적으로 개발하기

2026년 11월 15일 · @quattroro

현실적인 목표는 처음부터 맞게 짜는 것이 아니라, 틀렸을 때 싸게 고칠 수 있게 유지하는 것이다. 실무에서 아키텍처는 처음부터 완벽하게 정해지지 않는다. 누더기 코드는 대부분 고치는 비용이 비싸서 땜질로 버티다가 생긴다.

버그 없는 결과물을 처음부터 만드는 방법은 없다. 대신 세 가지를 갖추는 것이 현실적인 최선이다.

- 버그가 생기면 금방 드러난다 (자동 검증)
- 원인이 좁은 범위에 있다 (모듈 경계)
- 고치기 싸다 (테스트가 받쳐 주는 리팩터링)

이건 AI가 없을 때도 좋은 팀이 하던 방식이다. 에이전트를 쓰면 이 습관이 있는 팀과 없는 팀의 차이가 더 크게 벌어진다.

## 1. 경계를 나눠 국소적으로 판단할 수 있게 하기

프로젝트가 커질 때 에이전트의 가장 큰 문제는 전체를 한 번에 볼 수 없다는 점이다. 사람도 마찬가지다. 그래서 모듈 경계가 중요하다.

- **역할과 인터페이스를 분명히 나눈다.** 변경할 때 그 모듈과 인터페이스만 보고도 맞게 판단할 수 있다.
- **디렉토리별로 짧은 CLAUDE.md나 AGENTS.md를 둔다.** "이 모듈은 무엇을 하고, 외부에는 이 인터페이스만 노출하며, 이런 규칙이 있다" 정도면 충분하다. 에이전트가 그 폴더에서 작업할 때 필요한 맥락만 읽는다.
- **작업 단위를 작게 쪼갠다.** "전투 시스템 개선"보다 "데미지 계산 함수에 크리티컬 추가"처럼 한 모듈 안에서 끝나는 크기가 좋다.

경계가 잘 나뉘어 있으면 아키텍처가 바뀌어도 그 모듈 안쪽만 갈아엎으면 된다. 이것이 누더기 방지의 본질이다.

## 2. 검증은 층을 나눠서 자동으로

매번 전체를 검증하면 프로젝트가 커질수록 느려져서 결국 아무도 안 하게 된다. 그래서 비용에 따라 층을 나눈다.

|   |   |   |
|---|---|---|
|언제|무엇을|누가|
|매 변경|컴파일, 린트, 바꾼 모듈의 유닛 테스트|훅이 자동 실행|
|기능 단위 완료|관련 통합 테스트, 직접 플레이 확인|에이전트 + 사람|
|머지 전 / 매일|전체 테스트, 리플레이 회귀 테스트|CI|

- **에이전트가 기억해서 하게 하지 말고 자동으로 돌게 한다.** CLAUDE.md의 "테스트 돌려"는 지침일 뿐이라 빠질 수 있다. Claude Code의 hook이나 CI로 걸어 두면 강제된다.
- **테스트는 위험한 곳에 집중한다.** 충돌, 게임 규칙, 상태 전이, 저장 데이터처럼 틀리면 조용히 망가지는 로직은 결정론적인 유닛 테스트로 잡는다. 손맛, 연출, UI처럼 테스트로 잡기 어려운 건 사람이 플레이하는 게 효율적이다.
- **게임이라면 리플레이 테스트가 강력하다.** 시뮬레이션이 결정론적이면 입력 기록을 재생해서 결과 상태를 비교하는 회귀 테스트를 만들 수 있다. 프롬프트 실험에서 고정 타임스텝과 시드 난수를 요구한 이유도 이것이다. UE5라면 Automation Test 프레임워크와 Functional Test로 비슷한 구조를 만들 수 있다.

## 3. 정리를 습관으로 만들기

땜질이 쌓이는 건 막을 수 없으니, 쌓인 걸 주기적으로 걷어내는 것이 현실적이다.

- **기능 추가와 리팩터링을 섞지 않는다.** "기능 추가" 턴과 "동작은 그대로 두고 구조만 정리" 턴을 분리하면, 리팩터링 후 테스트가 깨질 때 원인이 명확하다. 테스트가 있어야 가능한 방식이라 1번과 2번이 이 습관의 전제다.
- **변경을 작게 유지하고 diff를 리뷰한다.** 에이전트가 만든 코드는 돌아가긴 하는데 구조가 미묘하게 어긋나는 경우가 많다. 작은 diff는 사람이 읽을 수 있다. 처음부터 맥락이 없는 별도 에이전트에게 리뷰를 시키는 것도 효과가 있다. 자기가 짠 코드는 자기 눈에 맞아 보이기 때문이다.
- **설계 결정을 기록한다.** "왜 이렇게 했는지"를 짧게 남겨 두면, 나중에 에이전트가 그 결정을 모르고 반대 방향으로 고치는 일을 줄일 수 있다.

## 사람과 에이전트의 역할 분담

구조를 정하는 건 사람, 그 안에서 만들고 확인하는 건 에이전트가 맡는다.

|   |   |
|---|---|
|역할|맡는 일|
|사람|모듈 경계와 인터페이스 결정, 무엇을 테스트할지 결정, 큰 구조 변경 여부 판단, diff 리뷰|
|에이전트|정해진 경계 안에서 구현, 테스트 작성과 실행, 리팩터링 수행|
